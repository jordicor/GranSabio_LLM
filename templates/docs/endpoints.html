Generate Content

POST /generate

Initiates content generation with multi-layer QA evaluation. Returns a session ID for tracking progress.

Request Body

prompt
string
Content generation prompt (minimum 10 characters)
request_name
string
Optional descriptive name for this request (max 128 chars). Returned in all responses and streaming events for easy client-side identification (e.g., "LinkedIn Article", "School Essay")
content_type
string
Type of content: biography, script, novel, article, essay, technical, creative, or json. content_type="json" is a legacy alias for requesting JSON output.
json_output
boolean
Set to true to request JSON output while keeping the declared content_type. Without json_schema, this uses JSON_LOOSE: extracts the first top-level object or array from common AI wrappers, unwraps fences, applies conservative repairs, and rejects missing JSON, unrecoverable truncation, expectation failures, and top-level scalars.
json_retry_without_iteration
boolean
When true, JSON validation errors on standard non-tool-loop generation trigger retries that do NOT consume main iterations (default: false). Tool-loop JSON contract errors fail fast and are not converted into this retry path. Controlled by MAX_JSON_RETRY_ATTEMPTS env var (default: 2 retries)
json_schema
object
Optional non-empty top-level object JSON Schema for JSON_STRUCTURED outputs (requires json_output=true or content_type="json"). json_schema={} is rejected; omit the field or pass null for flexible JSON. See JSON Schema Structured Outputs for details.
json_expectations
array
Optional path-based validation rules for specific JSON fields (requires json_output=true or content_type="json"). Validates only specified fields without defining complete structure. See JSON Validation: Schema vs Expectations for comparison and usage.
target_field
string
Path to one primary text field in JSON output using jmespath notation. Examples: "generated_text", "data.content". The alias text_field_path accepts the same single path; lists are rejected with HTTP 422 before generation. Required only when downstream text validators or QA must operate on a specific string field; pure JSON validation can accept object/array JSON without extractable text. See Smart Editing for details.
text_field_only
boolean
Controls what QA/Consensus/GranSabio receives when processing JSON. If true: Send only extracted text field(s) for evaluation (saves tokens). If false: Send complete JSON with hint about primary fields. In both cases, the user always receives the complete JSON with all fields preserved. (default: false)
project_id
string
Optional project identifier (≤128 chars) to group related sessions. Reuse the value returned from a previous negotiation.
request_project_id

temperature

max_tokens

🚀 QA Bypass Mode

For rapid content generation without semantic QA evaluation, send an empty qa_layers array. The LLM preflight gate still runs before generation and can reject contradictory or unsupported requests.

Bypass Example

JSON 
{
  "prompt": "Write a short science fiction story about AI",
  "content_type": "story",
  "generator_model": "gpt-4o",
  "temperature": 0.8,
  "max_tokens": 1000,
  "qa_layers": [],  // Empty array = skip semantic QA layers
  "max_iterations": 1,
  "verbose": true
}

Bypass Behavior

  • Post-Preflight Approval: After preflight passes, content is approved immediately after generation
  • No Semantic QA Evaluation: Skips configured quality assessment layers
  • Preflight Still Runs: Contradiction and feasibility detection remains active
  • Perfect Score: Returns 10.0 score by default
  • Single Iteration: No retry loops, accepts first result

Bypass Response

{
  "status": "completed",
  "content": "...",
  "qa_result": {
    "approved": true,
    "global_score": 10.0,
    "bypassed": true
  }
}

Token Percentage Behavior

  • Dynamic Allocation: Automatically calculates tokens based on model's maximum output capacity
  • Safety Margin: Applies 95% safety margin to prevent token limit errors
  • Model-Aware: Adjusts to each model's specific limits (e.g., GPT-5: 32,000 tokens, Claude Opus 4: 32,000 tokens)
  • Takes Precedence: When specified, overrides the max_tokens field
  • Range: Accepts values from 1.0 to 100.0 (percentage)

Session Stream (SSE)

GET /stream/{session_id}

Everything one session produces, live, over Server-Sent Events: status transitions, generation drafts, thinking, QA / preflight / Arbiter / Gran Sabio content, control events and the final verdict. This is a session-scoped adapter over the same bus as /stream/project/{project_id} (not a second event bus), projected onto a flat contract. It is the endpoint the official SDK consumes.

Isolation: sibling sessions of the same project are never exposed — not in the initial snapshot, not through project aggregates, not through trigger_session. Each caller sees their own session.

Path Parameters

session_id
string
Session identifier returned from /generate (max 128 chars)

Query Parameters

phases
string
CSV of phases to subscribe, same names as the project stream. Default: "all"
visibility
string
full (default) or canonical. See Content Labels below

Event Types

connected
event
Always first. Carries session_id, project_id, subscribed_phases and the effective visibility
status_snapshot
event
Sent on connect. Flat status, current_phase, iteration, max_iterations plus the full session object; project only carries project identity/lifecycle
status_change
event
Same flat shape as the snapshot, emitted when this session moves
chunk
event
Content of this session, labelled with content_status, iteration, attempt_id and sequence
session_end
event
This session finished; the stream drains what it had pending and closes right after
stream_end
event
Stream closing. Always includes reason

Sequence and Gaps

Every content event carries a sequence that is monotonic per (session, phase). Delivery is best effort: a slow subscriber whose queue fills up loses events at transport level. A gap in sequence therefore means "you missed something", never "nothing happened" — check it instead of assuming continuity.

Close Semantics

  • Closes on its own session_end: the project stream stays open until the project ends; this one does not
  • Drains first: content still queued for this session is delivered before the close
  • Every subscription has a session terminal: session_end is fanned out over the content phases and over the status channel, so phases=status alone closes on its own session too; the duplicated copies collapse into the single terminal the client sees
  • Heartbeat every 15 seconds: SSE comment, transparent to EventSource clients

Example Usage (JavaScript)

JavaScript 
const eventSource = new EventSource(`/stream/${sessionId}`);
let draft = '';
let expected = {};

eventSource.onmessage = function(event) {
  const update = JSON.parse(event.data);

  if (update.type === 'status_snapshot' || update.type === 'status_change') {
    console.log('Status:', update.status, 'phase:', update.current_phase);
    console.log('Iteration:', update.iteration, '/', update.max_iterations);
    return;
  }

  if (update.type === 'chunk' && typeof update.content === 'string') {
    // Detect dropped events: sequence is monotonic per (session, phase)
    const key = update.phase;
    if (expected[key] !== undefined && update.sequence > expected[key]) {
      console.warn('Missed', update.sequence - expected[key], 'events on', key);
    }
    expected[key] = update.sequence + 1;

    // Drafts are deltas; any other content_status is the FULL body
    if (update.content_status === 'draft') {
      if (!update.is_thinking) draft += update.content;
    } else {
      draft = update.content;  // accepted / rejected / filtered commit
      console.log('Commit:', update.content_status, 'iteration', update.iteration);
    }
    return;
  }

  if (update.type === 'session_end' || update.type === 'stream_end') {
    eventSource.close();
  }
};

// Note: SSE heartbeat comments are automatically handled by EventSource

Unified Project Stream (SSE)

GET /stream/project/{project_id}

Stream real-time events for all sessions under a project using Server-Sent Events (SSE). Select which phases to receive via the phases query parameter.

Live-Only Streaming: This endpoint does NOT replay historical data. It only emits events generated after the client connects. If you need to recover past content, your client application should persist events as they arrive.

Path Parameters

project_id
string
The project identifier (max 128 chars)

Query Parameters

phases
string
CSV of phases to subscribe, including auto_qa, preflight, generation, qa, consensus, gran_sabio, and status. Default: "all"
visibility
string
full (default) delivers everything labelled; canonical omits drafts and thinking. Default: "full"

Content Labels

Every content emission says what it is, so a draft can never be mistaken for the result. These fields are additive and orthogonal to status, which carries session/project lifecycle.

content_status
string
draft (work in progress, may be superseded), accepted (validated canonical commit), rejected (discarded by the engine), filtered (stopped by provider content policy)
iteration
integer
Pipeline iteration the emission belongs to
attempt_id
integer
Monotonic attempt inside the session+phase. A change means the previous attempt was replaced: reset any cursor kept on it
sequence
integer
Monotonic per (session, phase). Delivery is best effort, so a gap means events were dropped — never that nothing happened
is_thinking
boolean
Provider-reported reasoning stream (also carried as subphase: "thinking"). Never inferred from the text
Commits replace, they do not append: a chunk labelled anything other than draft carries the FULL body of its attempt (accepted_stream, accepted_json, tool_loop_final, rejected_json), not a delta. A consumer that accumulates drafts must REPLACE what it has for that (session, phase) when one arrives, or it will show the dead draft glued to the text that supersedes it.
visibility is a convenience filter, not a permission: canonical drops content_status="draft" chunks and thinking — including inside the initial late-join snapshot — and keeps status, control, accepted and terminal events. Use it when you only want the committed view; the default full is the live view (drafts, thinking, discarded attempts) that lets you stop a run before paying for its output.

A Gran Sabio review envelope did not pass its contract
status_change
event
Session state changed (status, phase, iteration, QA progress)
session_end
event
A session within the project completed or failed
stream_end
event
Stream closing (project ended or cancelled). Always includes "reason"

Key Behaviors

  • All events include "phase" field: Easy client-side filtering by origin
  • Heartbeat every 15 seconds: SSE comment : heartbeat keeps connection alive
  • Immediate close on cancel: No queue draining - stops immediately
  • Guaranteed close event: Client always receives stream_end with reason

Example Usage (JavaScript)

JavaScript 
const projectId = 'my-biography-project';

// Subscribe to generation, QA, and status phases
const eventSource = new EventSource(
  `/stream/project/${projectId}?phases=generation,qa,status`
);

eventSource.onmessage = function(event) {
  const data = JSON.parse(event.data);

  // All events have "phase" field for easy filtering
  switch (data.phase) {
    case 'generation':
      appendToEditor(data.session_id, data.content);
      break;

    case 'qa':
      updateQAPanel(data.session_id, data.content);
      break;

    case 'status':
      if (data.type === 'status_snapshot') {
        initializeDashboard(data.project);
      } else if (data.type === 'status_change') {
        updateDashboard(data.project);
      } else if (data.type === 'stream_end') {
        console.log('Stream ended:', data.reason);
        eventSource.close();
      }
      break;
  }
};

eventSource.onerror = function(error) {
  console.error('Stream error:', error);
  eventSource.close();
};

Get Final Result

GET /result/{session_id}

Get the final result of a completed generation session.

The response mirrors the original request metadata, including project_id when the session is part of a grouped project.

Failed sessions carry no draft: when a session ends on an unusable provider finish (content_filter, pause_turn, provider_error…), content holds the last accepted text or an empty string — never the partial draft the provider had emitted. That draft is unvalidated, so it stays out of the canonical payload; only its size travels here, as partial_content_chars inside failure_reason. Combining with Unified Stream

For a complete control panel experience, use the unified stream endpoint instead of polling:

JavaScript 
const projectId = 'my-biography-project';

// Single connection for status + generation chunks
const eventSource = new EventSource(
  `/stream/project/${projectId}?phases=generation,status`
);

eventSource.onmessage = function(event) {
  const data = JSON.parse(event.data);

  switch (data.phase) {
    case 'status':

      break;

    case 'generation':
      appendToEditor(data.session_id, data.content);
      break;
  }
};
Polling vs Streaming: Use this endpoint for periodic status snapshots (dashboard refresh). For real-time updates, use the unified stream endpoint: /stream/project/{id}?phases=status (status only) or /stream/project/{id} (all phases).
